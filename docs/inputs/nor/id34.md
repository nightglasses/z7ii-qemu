# ID34 source inventory

The inventory and original-updater comparison located **no usable,
authenticated whole ID34 record**. Z7II C1.70 and freshly retrieved Z6II C1.70
identify the same external descriptor17 record. Z7 C3.80 has a different ID34
registry span. These identified loader paths and byte comparisons do not prove
that every byte of every updater lacks a default. Field semantics and the
different startup requirements are recorded in
[the consumer analysis](../../runtime/id34.md).

Original-record recovery and functional emulation are separate objectives.
The explicit [constructed profile](functional.md) now demonstrates mapper
return and later manager progress using constrained geometry and declared
scalar hypotheses. No claim of recovered original bytes follows from that
success; missing factory data does not block further functional investigation.

## Direct byte observations

Primary input: `02_eg1840_mas_01700.payload.bin`,
38,239,096 bytes, MAS VA base `0x10020000`. Offsets below are payload file
offsets, not updater-container offsets. The read-only extraction is retained in
`run id34inventory/inventory.json`.

| Object | Payload offset | MAS VA | Little-endian words |
|---|---:|---:|---|
| ID17 descriptor prefix | `0x23d8844` | `0x123f8844` | `132c0000, 0, 20000, 1fffc` |
| ID34 registry row | `0x23d8ebc` | `0x123f8ebc` | `22, d700, 0, d00, 0, 11, 11` |
| ID34 loader manifest row | `0x18b0b20` | `0x118d0b20` | `d700, c00, 220300, 1` |

The manifest begins at MAS VA `0x118d0a20`; ID34 is row 16 (zero based).
Together with the retained loader analysis in
`run descriptor/static.json`, the mapping is descriptor17 external
NOR `[0x132c0000,0x132e0000)`, phase 3, source
`[0x132cd700,0x132ce300)`, copy length `0xc00`. The registry's `0xd00` is not
the manifest copy length and is not evidence of a ROM object.

The existing [descriptor boundary](descriptor.md) records destination
`0xb7f57700` within parent `0xb7f4a000`, and callback
`0x1020fa27 → 0x10217942 → 0x1021796a`, whose translator reads the pointer at
`0xb185f82c`. These callback details are retained analysis, not new execution
observations from this inventory. Translator dimensions at `+0x1c/+0x20` fit
30/20 and `+0x24/+0x28` fit 8/8; these bounds do not recover numeric tables.

Scoped file inventories covered this repository's `work/`, the adjacent
`../nightglass` and `../nightglass-firmware` trees, and firmware/model filename
matches in the developer's local project collection. That broader search was
noisy and paged; it is not a complete inventory of every local file. No further
same-architecture original machine payload was identified. Downloads top-level
metadata supplied no firmware candidate. Generated build trees, reconstructed
source resources and runtime RAM captures are not updater defaults.

`docs/refmap/REFS.tsv` retains references to historical
`resource34-schema`, `id34-producer-format`, `z6ii-id34-compare`,
`z7-resource34-compare` and `wl-z7-id34-audit` receipts. Their referenced
`receipt.md` files are absent locally; an index reference does not substitute
for those primary artifacts. Fresh package evidence below replaces reliance on
those missing receipts for the stated byte comparisons. No active IDA database,
firmware, device model or guest state was changed, and no QEMU/GDB run was
performed.

For factory-data recovery, the next decisive source is an authentic descriptor17 capture containing the
whole `0xc00` ID34 record, or a newly identified compatible original ROM object
with traceable loader evidence. Until then, the defensible conclusion is
“no usable original ID34 located,” not “a translator or string proves a default.”

The subsequent [structural survey](candidates.md) retains 296 candidate windows
from five original payloads, with no authenticated ID34 object. The
[producer follow-up](../../runtime/id34.md#re-read-persistence-and-settings-are-distinct-paths)
also distinguishes external-resource re-read, caller-buffer persistence and
ordinary settings; none of those identified paths supplies original ID34
values. A full descriptor17 capture remains preferable because later phase-3
record bodies also remain unverified.

## Official updater availability

Nikon's live [Z6II download page](https://downloadcenter.nikonimglib.com/en/download/fw/560.html)
identified exactly C1.70, file `Z6_2_0170.bin`, approximately 46.73 MB;
the live [Z7 download page](https://downloadcenter.nikonimglib.com/en/download/fw/558.html)
identified exactly C3.80, file `Z_7_0380.bin`, approximately 32.88 MB.
The inspected page HTML exposes official download redirect links for
[Z6II C1.70](https://crossgate.nikonimglib.com/dsd_redirect/redirect.do?P=JYsyI77&R=d1JXY20&L=oiPro07&O=NbiR200)
and [Z7 C3.80](https://crossgate.nikonimglib.com/dsd_redirect/redirect.do?P=ikdq374&R=ycEng19&L=WiqXi07&O=8Z9TP00).
The parent then retrieved the two binaries through those official redirects:
49,002,888 bytes for Z6II and 34,472,614 bytes for Z7. The existing adjacent
`nightglass/src/nightglass/container.py` parser decoded the packages and
validated every component CRC and the package CRC before extraction. Original
downloads, extracted payloads, manifests and comparisons remain ignored under
`run id34official/`.

All offsets in this comparison are **MAS payload file offsets**, with VA base
`10020000`:

| Observation | Z6II C1.70 | Z7 C3.80 |
|---|---:|---:|
| MAS payload length | 38,750,136 | 33,052,088 |
| ID17 descriptor prefix | `23e04fc` | `1efcbb4` |
| ID34 registry row | `23e0b74`: `22,d700,0,d00,0,11,11` | `1efd0cc`: `22,d700,0,1900,0,11,11` |
| Z7II-identical 25-row manifest | `18b7374`, including ID34 at `18b7474` | No exact manifest match; not a record-absence proof |

Z6II's resource getter/initial command starts at MAS VA `10217932`, and the
mapper at `1021795a`; native disassembly confirms `+774`, the same scalar
offsets, and the `+24/+28` loop reading `+42c` with 32-byte row strides. The
Z7II-identical rectangle-helper prefix occurs at Z6II MAS VA `10255d44`.

The existing seed's ID24/25/27 bodies match Z7 MAS ROM exactly at payload
offsets `1500d04`, `1501204` and `1501104`, respectively. This rechecks their
original-byte provenance without extending it to ID34. `compare.json`,
`verified.json`, `id34manifest.json` and `z6translator.dis` retain the scoped
comparison. Neither updater's component directory supplies a separately
identified factory-NOR dump; no compatible whole ID34 body was recovered from
the inspected paths.

## Public same-family inputs

Fixed public source inspection also found no identified compatible original
ID34 object:

- Z7 commit `97abf0b81cd3211f8374a38987a0beaf4549b90f`
  [requires user-supplied MAIN](https://github.com/WonderLantern/z7-qemu/blob/97abf0b81cd3211f8374a38987a0beaf4549b90f/docs/firmware.md).
  Its [interactive initialization](https://github.com/WonderLantern/z7-qemu/blob/97abf0b81cd3211f8374a38987a0beaf4549b90f/tools/interactive.py#L427-L456)
  changes RAM state and selects an empty calibration table; those operations
  are not an original NOR record.
- Z9 commit `b828c7eeb3336f061a2b7ffde58c872fe04c8d83`
  [extracts a group12 ROM default](https://github.com/WonderLantern/z9-qemu/blob/b828c7eeb3336f061a2b7ffde58c872fe04c8d83/tools/parameter_input.py)
  from user-supplied C5.32 MAIN at VA `44ab18c0`, length `20000`, and replaces
  the final four bytes with `ENDM` for loading at `462e0000`. The source
  explicitly distinguishes this input from a hardware-calibration dump. No
  mapping establishes equivalence to Z7II descriptor17/ID34. Its
  [sequence input](https://github.com/WonderLantern/z9-qemu/blob/b828c7eeb3336f061a2b7ffde58c872fe04c8d83/tools/z9_sequence_resource_input.py)
  supplies a footer while leaving the body unrecovered.

These are dispositions of concrete published input paths, not a whole-ROM
absence theorem. Connected Drive searches for the project, models and ID34
returned no candidate in this session.
