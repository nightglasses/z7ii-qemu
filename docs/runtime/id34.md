# ID34 fields and startup requirements

Scope: ID34 is a descriptor17 external record, not a ready-bit
producer. Original Z7II C1.70 code consumes it during phase-3 initialization.
The partial display input exposes erased dimensions and an out-of-bounds
translation before worker startup. This note identifies structural and numeric
dependencies; it does **not** establish a minimal replacement record that boots.
The subsequent explicit [functional input](../inputs/nor/functional.md) makes
the mapper return and reaches manager current worker 4/state 2 before a graphics
stream rejection. Factory calibration recovery remains a separate objective.

Addresses below are **Z7II C1.70 MAS VA**, unless explicitly qualified. Record
offsets are relative to the beginning of the `0xc00` copied ID34 body. The
[source inventory](../inputs/nor/id34.md) distinguishes original package bytes,
external records and experimental inputs.

## Source and immediate consumer

The phase-3 manifest at `118d0b20` selects descriptor17 offset `d700`, length
`c00`, ID34. The original resource path is:

```text
external NOR 132cd700..132ce2ff
  -> 103c05f4: descriptor17 validation, phase selection and copy
  -> resource 34 publication, event 04400045
  -> callback 1020fa27 -> 1020f9d4(1)
  -> 10217942: resource getter 103a47a2(34), pointer at b185f82c
  -> 1021796a: translate into b213f834, workspace length 274
```

In the retained partial-input execution the copied record is at `b7f57700`.
Its outer `ENDM` succeeds, but the body remains erased. Publication therefore
does not certify the numeric record. The loader and current baseline failure
are documented separately in [resource.md](resource.md).

Before the mapper, `10217942` reads the 32-bit word at `+774`, negates it and
passes that value together with signed halfword 6 through `1035d396`. The
follow-up trace below resolves this as a paired parameter-store operation:
**6 is a parameter value, not an EX command number**. Its physical quantity and
valid numeric range remain unknown. No original calibration-value generator
has been identified by this consumer trace.

## Fields established from original instructions

| ID34 offset | Established operation | Consumer and constraint |
|---|---|---|
| `+1c`, `+20` | Raw-grid column and row counts | `10215b0a`: 16-bit input row stride 60, 32-bit output row stride 120; fixed raw buffer is 1200 bytes, supporting at most 30 columns by 20 rows |
| `+24`, `+28` | Aggregated-grid column and row counts | Mapper and later helpers use 32-byte rows and fixed 8-by-8 arrays; each count must be at most 8 |
| `+2c..12b` | 8-by-8 table of rectangle starting columns, `x0` | Passed by `10215432` to `10255fe4` |
| `+12c..22b` | Rectangle starting rows, `y0` | Same call; 32-byte table row stride |
| `+22c..32b` | Rectangle ending columns, `x1` | Inclusive endpoint |
| `+32c..42b` | Rectangle ending rows, `y1` | Inclusive endpoint |
| `+42c..52b` | First 8-by-8 coefficient table | Active cells multiplied by 4 into derived `+d0` at initialization; read again by `102173ea`, then normalized by `10256434` |
| `+52c..62b` | Second 8-by-8 coefficient table | Read and multiplied by 4 in `10216ec2` at `10217174..10217198`, then normalized by the same helper |
| `+14`, `+18`, and scattered words `+62c..7c8` | Scalar parameters, with explicit per-field scaling | Mapper has 83 scalar assignments in addition to its matrix; most scale by 4, some remain raw, and `+684/+70c/+710` scale by 96 |
| `+774` | Negated value stored in parameter `40000405`; paired parameter `40000406` receives 6 | `10217942 -> 1035d396`; also read into a later report at `10217ce4` |

The 83 assignments include the six header words `+14..28`; they are not 83
additional words after the header. The exact source/destination/scale map is
retained in `run id34fields/scalar.json`. This is a mapper
inventory, not an exhaustive schema for all `0xc00` bytes.

The raw-grid conversion reads `u16 sample[row*30+col]` and stores
`((3*sample)>>5) & 0x3fffff` in a 30-column 32-bit grid. `10215432` subsequently
uses the four coordinate tables to form the smaller grid. For each active
output cell, `10255fe4` sums an inclusive rectangle and divides successively by
`abs(x1-x0)+1` and `abs(y1-y0)+1`; `10255fd0` implements the signed absolute
difference. Its loops compare endpoints as unsigned values and do not repair
invalid coordinates. For a meaningful nonempty grid, the source must satisfy:

```text
1 <= raw_columns <= 30, 1 <= raw_rows <= 20
1 <= output_columns <= 8, 1 <= output_rows <= 8
0 <= x0 <= x1 < raw_columns
0 <= y0 <= y1 < raw_rows
```

The lower bound 1 here describes an active grid; it is not a claim that the
firmware rejects zero counts. Zero counts can skip work and do not establish
a valid operating configuration. Reversed endpoints can skip sums, while an
erased `ffffffff` endpoint can cause a very long or wrapping loop. Bounds on
the four dimension words alone therefore do not validate the coordinates.

`10256434` subtracts the active maximum coefficient, converts each difference
through `102556d8`, sums the responses, and computes rounded normalized weights
with numerator `192*response`. A zero sum uses divisor 96. `102556d8` uses a
96-entry fractional lookup and integer shifts, with absolute input clamped at
2303; in the positive unsaturated range an increase of 96 approximately doubles
the response. Thus these tables have a log-domain weighting role, rather than
being an arbitrary array of linear samples. Exact photographic units or named
metering modes are **not established** by this arithmetic.

Scalar consumers also establish distinct roles, without recovering their
factory values:

- `+62c -> derived +34` is subtracted before a zero clamp by `10255a48`.
- `+630 -> derived +38` is subtracted before a lower-limit selection by
  `10255b3a`.
- `+66c/+668 -> derived +3c/+40` provide the ordered clamp endpoints used by
  `10255bbe`.
- Raw `+18 -> derived +5c` multiplies an exponential response in the threshold
  calculation at `10255d1e`.

Other original consumers directly read words outside this mapper's assignment
list, including `+678`, `+6a4`, `+734`, `+738`, `+744` and `+7bc`. Unknown header
words, gaps and the tail are not certified unused. Calling the object a
grid-statistics/weighting parameter record follows its operations; identifying
it as a particular factory exposure calibration remains an inference.

## What is actually needed next

There are three different requirements, with different evidence:

1. **To remove the observed mapper overrun:** `+24/+28` must fit the fixed
   8-by-8 destination, and the corresponding active `+42c` cells must be backed
   by the copied record. This is a structural necessary condition for the
   intended active-grid path, not proof that chosen values boot.
2. **To reproduce factory parameterization:** the `+774` parameter value,
   the mapper's 83 scalar inputs and active first coefficient table need a
   traceable source. The mapper reads them on its normal path, including those
   after the matrix loop. Static reads do not prove that every numeric value
   independently gates startup, nor establish that erased scalar values are
   acceptable.
3. **To operate the later grid processing:** the raw dimensions, active rectangle
   coordinates, both coefficient tables and relevant scalar limits/biases must
   agree. The raw-grid work is reached through later context/data processing
   (`10210e6e`, called from `10321654`), not unconditionally by the initial
   phase-3 callback. No measured startup minimum has been isolated for those
   later fields.

The loader copies the whole `0xc00` body. That does not imply every byte has an
independent boot role. Static constraints do not uniquely recover factory
values; a functional profile may instead make explicit virtual-camera choices
and numeric hypotheses, then validate the original consumers. The first such
[experiment](../inputs/nor/functional.md) now observes translator return and
manager progress. It does not establish safe later arithmetic for all its
unvalidated scalar values. An authentic Z7II or qualified same-schema capture
would improve fidelity, but is not a prerequisite for that functional route.

## Parameter-store follow-up

Native instructions at `1035d39a` load two encoded parameter IDs from ROM
`118e609c`: `40000405` and `40000406`. `1035d396` passes count 2, those IDs,
and values `{-ID34[774], 6}` to `1026b5e8`. The latter acquires the registry
mutex through `1026c0d2 -> 10360f2e(...,1000)`, calls `102c9b42`, and releases
the mutex through `1026c0de`. `102c9a88` resolves group `04` to base
`b23dcbf8`; `102c9b42` performs ordinary 32-bit stores:

```text
b23dcc0c := -ID34[774]  // encoded ID 40000405
b23dcc10 := 6           // encoded ID 40000406
```

Both shared tails in this path are native function epilogues. There is no EX
transmit or hardware-completion event in this setter; the mutex operation is
a separate synchronization mechanism. This corrects the earlier over-specific
description of halfword 6 as a command number.

A fresh single-hardware-breakpoint probe, using the existing unchanged bundle,
existing build, multi-thread TCG and the same explicit partial display seed,
stops at mapper entry `1021796a` and directly observes:

| Object | Value |
|---|---|
| Resource 34 pointer | `b7f57700` |
| Source `+774` | `ffffffff` |
| Parameter `40000405`, at `b23dcc0c` | `1` |
| Parameter `40000406`, at `b23dcc10` | `6` |
| Four dimensions `+1c/+20/+24/+28` | all `ffffffff` |
| Installed rear-panel pointer | `b7f54a00` |
| Manager current/target/state | `5/5/0` |

Thus this setter returns before the invalid matrix loop; it is not the
observed missing completion in that partial-input run. The probe reads guest
memory only, performs no replacement-record injection, and makes no first-frame
claim. Actual argv, GDB script, log and owned-process cleanup are retained in
`run id34producer/parameter.*` and `run.py`.

## Re-read, persistence and settings are distinct paths

Further original-code tracing narrows the possible data producers:

- Getter `103a47a2 -> 103bfaa2` returns the registry RAM pointer. Alternative
  getter `103bfab8` returns backing-base plus resource offset; for ID34 that
  resolves to external `132cd700`, not a ROM template.
- The single-resource reload selector `103a4b90(34)` reaches `103c07fe` with
  the descriptor17 manifest and phase argument 9. Its native switch has an
  ID34 case, but the handler again validates and reads the external backing.
  It does not create a record when `ENDM` or the body is absent. Identified
  direct callers of this selector request other resources; an automatic
  cold-boot call for ID34 is not established.
- Read API `103a48c0 -> 103bf7d4 -> 103bf3c6` reads existing backing into RAM.
  Write API `103a48cc -> 103bf6cc -> 103bf6b2` takes caller-supplied RAM and
  reaches the erase/program helpers, including `102a7e98 -> 102a7d2e`.
  These operations transfer existing data; the traced helpers contain no
  numeric ID34-default construction.
- The 82-row settings-persistence table at `118fab04`, used by `1010261e`
  and `101026b4`, has resource-byte counts `{0:28,15:49,13:1,14:1,16:1,7:1,68:1}`.
  It contains neither ID17 nor ID34. This concrete ordinary-settings path is
  not authority to restore the missing descriptor17 calibration record.

These are dispositions of identified paths, not a proof that every firmware
service has been exhaustively audited. Native reload disassembly, the original
settings table, helper decompilations and the manifest remain in
`run id34producer/`.

The [ROM structure survey](../inputs/nor/candidates.md) additionally checked
five original MAS/SLA payloads. Its 296 windows satisfy only selected geometry
constraints; none has an authenticated ID34 source link. The denser all-one
examples are inside a separate eight-word tuple table returned by
`102cec74(a,b) = 119ba598 + 288*a + 32*b`; a caller at `1035d68a` multiplies
its first four words by the corresponding last four. The same getter sequence
in Z6II returns base `119cae8c`. These containing-object consumers do not
establish an ID34 record boundary, so those windows are not adopted as inputs.

## Input scope before the next startup run

ID34 is the **first established invalid-record overrun**, not the only record
left unverified in the partial display seed. The phase-3 manifest selects
ID19/20 before it and the following rows after it:

| ID | Descriptor offset | Copy length | Identified callback use |
|---|---:|---:|---|
| 35 | `e400` | `c00` | `1020fa26` selects case 4; `10248802` caches the pointer |
| 36 | `f100` | `f00` | Same callback selects case 7, then `102487f0 -> 1024899a` |
| 39 | `11500` | `2c00` | `1021c83c`, registered by `1021f198` |
| 40 | `14200` | `200` | `10442752`, registered by `1044278e` |
| 41 | `14500` | `200` | `1020fa26` case 10 and `1021c83c` registrations |

These static selections and registrations do not prove that each erased body
will independently block startup. Their execution after ID34 has not been
validated. They do show why a whole original descriptor17 capture is preferable
to declaring an isolated ID34 replacement sufficient. A capture should retain
the complete `20000` bytes, including footer at `1fffc`, with model/version and
acquisition provenance. A traceable `c00`-byte ID34 capture would still be useful
evidence, while the other persistent inputs remain explicit unknowns.

For the functional objective, full factory capture is optional. The later
[constructed ID34 experiment](../inputs/nor/functional.md) demonstrates that
the selected nonempty geometry and scalar hypotheses permit initialization
and worker progress despite those other unverified inputs. This does not
establish their complete downstream validity.

## Evidence and limits

`run id34fields/` retains original-byte decompilation in
`static.txt`, native GNU Thumb disassembly in `fields.dis`, `scalar.json`, and
`additional.json` for the normalization, distance and scalar helpers. Literal
pools inside disassembly ranges are data, not additional instructions.

The separate original-updater comparison is retained under
`run id34official/`; its package CRCs and all component CRCs pass
the existing container parser. The producer follow-up adds the separate
read-only mapper-entry run above; the original field-analysis turn had no
QEMU/GDB run. Neither investigation changes firmware/device code or generates
a replacement record. Previous dynamic overrun receipts remain those in
[resource.md](resource.md).
