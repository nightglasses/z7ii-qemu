## Supported interface and explicit virtual assumptions

Aligned32-bit accesses implement the original count−1, source, destination, two configuration words, auxiliary configuration, request/control and low4 pending status. Local+1c, channel holes and other widths reject. Default ordinary copy requires configuration30f00/30f00, auxiliary0 and mode1 request11109003; all six data/configuration words must first be written by the guest. Fixed-source fill, other formats and transformations reject before changing their registers. The two-bit field3 is an original supported profile value; it is not interpreted as an eight-byte beat size.

The virtual profile starts with zero registers, no configured fields, global disabled and no pending work. Global bit28 enables the controller. Clearing it cancels outstanding channels even if other selectors remain set. The original finite bit20/24 RMW selectors share this word and retain their configured values. Their physical roles remain unknown: the named virtual profile treats them as configuration inputs, with local requests still producing copies and completion. It does not claim that those fields have no effect in hardware. Changing them never submits a transfer, invents status or emits an IRQ; all other global bits reject. A local control write clearing both active bits cancels that channel; active configuration changes reject. Cancellation produces virtual error status1, never success8. Reset cancels timers and clears configuration, progress and IRQs.

Each channel retains independent progress and a QEMUTimer. The nominal independent48MHz upstream Clock paces at most256 byte transactions per event; this is a virtual byte throughput convention, not a measured peripheral rate or EXPEED performance. Actual copies use pinned QEMU [dma_memory_read/write](https://github.com/qemu/qemu/blob/4fc49f46dc95d4a27de2509e7fceb2931e91faeb/include/system/dma.h#L146-L173). This default profile sets normal-memory-only transaction attributes: device/MMIO copies are outside its supported scope. Unknown source/target produces the actual bus failure and virtual error status1. There is no zero source or clipping to an available backing.

Only a fully successful transfer produces status8, informed by the original waiter's exact success comparison. Source and destination advance by accepted bytes. The count snapshot is explicitly modeled as max(remaining−1,0); physical residual encoding remains unknown. Progress commits after each successful chunk; an error can retain bus side effects within its failing chunk, as allowed by the upstream bus result. Status1 is a named bus-error/cancellation convention, not a recovered physical error bit. Guest clear-to-zero acknowledgement removes pending state; the original status and local control RMW paths remain responsible for clearing it. IRQ is generated from pending status and the original configuration bit15. The host never calls a guest ISR or sets an event flag. State is explicitly unmigratable.
