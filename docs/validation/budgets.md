# Synthetic fixture virtual deadlines and diagnostic budgets

This work solely corrects the wait budget for synthetic device tests. Device C implementations, original MAS runtime timing, 5-second host acceptance timeouts, and `-icount shift=0` settings remain unchanged. CODE is pinned at `fb05c3f40a049e4cc9f3c0aa84237c2b7e5ea114`; changes affect only the [pinned synthetic test runner entry](https://github.com/mashiro01/nightglass-qemu/blob/fb05c3f40a049e4cc9f3c0aa84237c2b7e5ea114/scripts/device-smoke-test.py), maintained as `scripts/devices.py`. These small generated 4-byte instruction inputs do not constitute recovered firmware.

GitHub Actions run `37840824780` compiled successfully and subsequently stopped at `timing-reset-cancels-pending: final loop not reached`. The uploaded fixture `synthetic.bin` is byte-identical to pre-fix generator `2dd05337a79093039d065702a88a5b70970d1b20`. The uploaded CI log omitted PC at failure time, precluding exact Linux stop point reconstruction. During read-only replay of the identical input, the original 2 ms settle window spent its time polling CNTP_CTL at `100200f4/100200f8/100200fc`, finally reaching self-loop `10020118` at 3.678845 s with R1=5 and clean exit. This replay utilized native binary `578f2610ff7697e9be3c00ecaffdb88df126f975` rather than remote publication binaries; no device transaction error occurred. Receipts reside in `work/issue331/ci-timing-wait-probe-578/result.json`.

With `icount shift=0`, virtual nanoseconds correlate with executed instruction count; long busy loops magnify host CPU workload, meaning host wall time cannot represent virtual time. The revised budgets are derived from individual device Clock and event models: cancellations and pauses occur before scheduled completion, and result assertions take place after the canceled operation would have completed. True completion paths continue to poll causally generated device status bits rather than asserting completion after fixed host sleeps. See official [icount documentation](https://github.com/qemu/qemu/blob/4fc49f46dc95d4a27de2509e7fceb2931e91faeb/docs/devel/tcg-icount.rst) for upstream semantics.

| Four-channel copy cancel | 513 bytes, <=256 bytes per chunk at 48 MHz yields ~10.7 us; cancel prior | 20 us, asserting destination unchanged and virtual cancel/error state |

These deadlines reflect virtual device models implemented in `hw/nikon/devices/`: `usio.c` frame, `spi.c` frame schedule, `i2c.c` period/schedule, `timing.c` Clock/expiry, `audio.c` drain/`hdmac.c` beat, and `copy.c` chunk schedule. They do not represent Nikon baud rates, physical camera latencies, EXPEED benchmark performance, or physical audio codecs. Shortening the timing period concurrently updates the one-shot count assertion to 30000 without weakening result guarantees.

Other long CNTP wait budgets have been audited: `secure-timer` and original active-init fixtures retain 48000 ticks, verifying the 48MHz/1ms/PPI29 software baseline; `timestamp-whole-guest-init` retains 48000 ticks; `timestamp-elapsed-freeze-carry` retains freeze, 32-bit carry, and elapsed>=4800 constraints; `clock-pll-start` maintains non-icount lock verification. None uses the failed busy-wait pattern. Successful completion paths for completion, MXIC, SPI, HDMAC, I2C, and copy rely on actual status bits and IRQs without arbitrary 1 ms settles. Global icount quanta remain untouched to avoid coalescing low-latency pending and cancellation sequences.

Focused verification evaluated the 21 fixtures affected by instruction generation or assertion changes; all 21 PASSED in 1.953951 seconds. Native binary is `578f261`, fixture is `fb05c3f`, and upstream is `4fc49f46dc95d4a27de2509e7fceb2931e91faeb`. Results in `work/issue331/wait-budget-fb05c3f/result.json` detail individual names, exit codes, bounds, and CI input equivalence checks. CI across the entire suite and unchanged MAS execution are conducted independently by the primary scheduler on publication heads.

If future normal or post-reset entry fails to reach the final self-loop within 5 seconds, a thin runner saves `wait-failure.json` (capturing phase, expected loop PC, final registers, and QMP status) and reports failure. This closes the diagnostic gap of missing failure PCs in historical logs without adding timeouts, retries, or fallbacks.
