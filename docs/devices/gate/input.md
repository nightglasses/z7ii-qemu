# Paired MAIN input transport

The finite gate input contract accepts one actual paired MAIN NV12 frame into
an owned type 0 slot 8 snapshot. Storage alone supplies backpressure; the
separately qualified [continuous processor](processing.md) consumes actual
pixels before publishing results. No software worker memory is read
by the device. The implementation is in `hw/nikon/devices/gate.c`; the typed
interface is declared in `include/hw/nikon/gateinput.h`.

## Source and observed connection

Addresses, offsets, masks and literal register words are hexadecimal.
Dimensions, pitches, byte lengths and counts are decimal. MAS code and
software-object addresses are C1.70 virtual
addresses; device register addresses are board physical addresses. Ranges
exclude their upper endpoint. Register packets contain little-endian words.

MAS `1030d020` allocates kind43 and `1030c214` constructs its descriptor. The
default ROM row at `119834b8` reserves `[40000000,40010000)`; the five mode
overrides are absent. The constructor specifically places the second plane
at base plus `8000`, rather than the ordinary pitch-times-height offset.
`1026405a` and `102be8a0` reuse that descriptor for the four MAIN phases.
This source establishes a special view, not an ordinary full-frame RAM pool.

An unchanged C1.70 photo execution under the declared virtual inputs retains
both worker 8 and worker 9 in ownership mask `300`. Worker9 has eighteen nodes.
Its type 0 resource 8 descriptor has width 1376, height 914, pitch 1408 and relative
plane offsets `0/8000`. Type5/resource 35 references that node as its predecessor.
The imported type 5 packet's logical register 0 also selects resource 8, matching
the original `102e2b7e` producer. The downstream graph has three type 10 branches
ending at type 0 resources3,4,5. Graph configuration is observed; pixel execution
and completion of those operators are not established by that snapshot.

The separate type 10/resource 53 belongs to worker 8 and ends at type 0 resource2.
Its software packet field at decimal offset156 is nonzero and selects bit4 of
the shared-route bitmap through `102e3560`. It is not the MAIN input selector.
The device does not use route `2690=141` as input qualification. CPU bridge
mapping to the separate SLA domain does not establish this pixel data route.

Interpreting the paired MAIN special view as a typed frame input to the matched
local slot 8 is an explicit functional wiring hypothesis. The device stores the
actual produced pixels; it neither expands the special view into frame RAM nor
discards writes while declaring an output complete.

## Accepted input and ownership

Qualification requires a committed slot 8 packet with word0 `09000201`, word1
`15500`, zero origin and unused planes, matching width/height and two identical
pitches, and relative Y/UV offsets `0/8000`. These are the finite observed setup
shape, not a general pixel-format or reserved-bit specification. The matching
type 5/resource 35 command port at `20100e60` must have successfully imported its
complete packet, with logical register 0 equal to 8. A processor start is not
required for input storage and is not generated by publication.

The supported virtual NV12 shape has nonzero even width and height, each at
most4096, and a matching pitch at least the width, aligned to 64 bytes and
bounded by the existing 17-bit pitch field. The published Y and interleaved UV
data are tightly packed: exactly width-times-height bytes followed by half that
many UV bytes. The largest stored snapshot is therefore 24 MiB. Guest pitch
padding is not copied into this internal representation.

`nikon_gate_input_status` returns unsupported, ready or busy and provides a
configuration generation token. Publication validates the same token, shape,
current qualification and both exact byte lengths before making an owned copy.
One successful publication makes the slot busy. The slot 8 availability query
at PA `20102060` returns nonzero while the actual queued input owns it;
configuration alone still does not make a slot busy. A second publication cannot
overwrite it. `nikon_gate_input_copy` reads the complete snapshot without
consuming it. A successful complete continuous graph retires the snapshot and
changes its generation. A single
frame is the explicit bounded functional storage choice, not a recovered
physical FIFO depth. Unmodeled processing cannot silently retire the frame.

Slot8 staging writes do not alter committed ownership. Its first parameter
commit or a changed complete commit cancels a queued frame and changes the
generation; a complete same-value commit preserves it. Type5/resource 35 reset
and every successful reload cancel the snapshot and change the generation.
An explicit gate stop does the same and blocks new input until reopening.
Whole-device reset clears the snapshot and counters while changing the token.
Cancellation never turns a frame into a processing result, pending bit or IRQ.

Read-only QOM properties expose the generation, cumulative accepted frame/byte
counts, queued width/height/stride/size, and `input-data`, which is base64 of the
tight NV12 snapshot or an empty string. These observations do not consume data
or alter the GUI. Reset clears the counters. The continuous processor exposes
its separate processed, error, cancellation, last-result and phase counters.

## Continuous activation

Continuous worker 9 has a different start path from ordinary per-node commands.
The original sequence `10264de0 → 102bc496 → 42193083 → 102e1b86 → 103894a0`
reaches `103b4e1e`. It calls `103bd08a` for the selected continuous input,
then `103bd288` for its type 1 control and reports start through the original
software callback. Only afterward does the photo caller start paired work.
A subsequent read-only observation records `20102100=121` and `20102608=1`:
the continuous input is enabled even though per-command active fields are zero.
Neither those zeros nor an unconsumed snapshot establishes a missing worker
start. The finite processor uses these continuous controls; it does not require
the ordinary per-command starts to execute this graph.

Photo initialization `10264972` sets VA `b18648f4` to one. On the first actual
paired raw event `1000`, callback `102637c2` decrements it without setting
`b1864850` event `400000`; later normal events have their separate notification
path. Raw event `400` only marks `b18648c0`, so adding a guessed four-frame FIFO
does not follow from that bit. Consumer `10268ba4` waits for `80400000`, records
a timeout and can fall through to decrement `b18648d8`. Negative counts therefore
do not prove a warmup FIFO depth. No host code repairs those counters or events.

The enabled finite graph now consumes the qualified MAIN input, calculates all
three output images and publishes its source-routed terminal causes. Releasing
the slot, overwriting it or emitting a terminal event without that work remains
prohibited. See [processing](processing.md) for admission, DMA and completion
assumptions, including the separately inferred whole-frame fence.

## Validation

The focused native stream fixtures compare every queued Y/UV byte, repeated
non-consuming diagnostic reads, source backpressure, slot 8 busy/readback,
cross-bank exclusion, changed-generation cancellation before DMA, stop, reload,
staging, repeated parameter commits and reset. The existing gate fixture also
passes independently. Native fixtures are separate from the original execution.
The earlier [capture receipt](/evidence/paired/capture.json) records the
input-delivery checkpoint. The [continuous receipt](/evidence/continuous/capture.json)
separates subsequent actual processing from the still-unpublished central GUI
scene and from physical-camera fidelity.
