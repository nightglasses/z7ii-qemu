# MEMC and Cortex-A7 diagnostic layer

This layer implements the next bounded contracts for [MEMC and early peripheral startup](/startup/memc) and [RTOS and multicore startup](/startup/smp). It preserves the original MAS bytes, reset entry `0x10020000`, ARM state, copy destinations and `O0x178` self-loop. The [previous original run](../../startup/first.md) stopped at the first `0x04264000` write. The [new parent-run receipt](../../startup/memc.md) records both MEMC stores accepted, the early stack PUSH passed, and the next uncovered read at `0x0428102c`; whole-camera boot remains unverified.

## Supported MEMC contract

The public [Fujitsu-copyrighted MEMC initialization source](https://github.com/hypoxic/stubby-1.60.1/blob/d670fe97469f4fbac35fcf67fbab81c7ea84f153/src/memc_init.S#L38-L59) names MODE bits `WDT[1:0]`, RBMON, WEOFF, NAND, PAGE and READY. It uses a different board address, `0xfff64000`. Binding that IP layout to MAS `0x04264000` is an explicit diagnostic hypothesis, not confirmed Nikon silicon identification. The public repository is a preserved source copy, not a verified vendor distribution. The [source match analysis](https://github.com/mashiro01/nightglass/blob/e5b3794b701852dd3030cedfe9f8a9571486130d/research/z7ii/qemu-memc-source-match.md) records the original MAS stores and limitations.

The separate SysBus MEMC device accepts only aligned 32-bit MODE0 at offset `0` and TIM0 at offset `0x20`. At reset neither register has a supplied value: each has an initialization flag, and reading a register before its own guest store returns `MEMTX_ERROR`. Successful stores and first rejected accesses are logged. MODE `0x21` and `0x29` are the implemented profiles: WDT=1 selects x16, PAGE=1, and WEOFF bit 3 respectively permits or disables external write enable. Guest read/modify/write of that bit is supported. Other profiles, widths and offsets fail; this does not mean every other value is invalid in the actual IP.

TIM0 accepts the original initialization profile `0x153b0902`. The [source's timing-field definitions](https://github.com/hypoxic/stubby-1.60.1/blob/d670fe97469f4fbac35fcf67fbab81c7ea84f153/src/memc_init.S#L94-L141) decode it as RACC=3, RADC=1, FRADC=10, RIDLC=1, WACC=12, WADC=4, WWEC=6 and WIDLC=2 cycles. The model stores this functional profile; it does not convert those fields into wall-clock or bus latency. Other timing profiles remain unimplemented.

The existing raw MAS image window becomes an upstream ROM device. [QEMU ROMD](https://github.com/qemu/qemu/blob/4fc49f46dc95d4a27de2509e7fceb2931e91faeb/include/system/memory.h#L1954-L1965) supplies direct reads from the loaded original bytes while sending guest writes to a device callback. Writes first require both MEMC registers initialized, then enforce WEOFF. With WEOFF clear, only aligned x16 access reaches the currently unsupported NOR backend and fails explicitly. No NOR command, erase, program, completion polling, page burst or writer has been implemented. WEOFF does not silently become a successful ROM write. The image window is a loader mapping assumption, not a recovered complete NOR aperture or capacity; command addresses outside that window remain uncovered and fail.

## CPU, IRQ, timer and RAM assumptions

Upstream Cortex-A7 cores replace the earlier Cortex-A9 diagnostic hypothesis to expose the generic timer used by MAS. The current machine defaults to two cores and supports explicit `-smp 1` or `-smp 2`; [the original two-core run](../../startup/smp.md) records the guest configuration evidence and real secondary wait path. This is not an identification of Nikon CPU type or physical core count. `reset-cbar=0x1d000000` and `cntfrq=48000000` are set before CPU realization through [upstream ARM properties](https://github.com/qemu/qemu/blob/4fc49f46dc95d4a27de2509e7fceb2931e91faeb/target/arm/cpu.c#L1305-L1309). The CBAR value comes from a candidate public SC2000 board configuration, not confirmed Z7II hardware. The [RTOS dependency analysis](https://github.com/mashiro01/nightglass/blob/e5b3794b701852dd3030cedfe9f8a9571486130d/research/z7ii/qemu-rtos-device-dependencies.md) distinguishes that candidate from the original MAS CBAR-reading and 48 MHz timer consumers.

The machine uses upstream A15MPCore with the selected CPU count and `num-irq=256`, including its 32 internal SGI/PPI IDs plus 224 external SPIs. [The upstream device](https://github.com/qemu/qemu/blob/4fc49f46dc95d4a27de2509e7fceb2931e91faeb/hw/cpu/a15mpcore.c#L55-L161) provides GICv2 Distributor at CBAR+`0x1000`, CPU interface at +`0x2000`, and genuine CPU IRQ/FIQ/virtual output wiring. It automatically connects secure physical timer to PPI 29, nonsecure physical timer to 30, virtual timer to 27 and hypervisor timer to 26. MAS must initialize and acknowledge the controller itself. No pending bit, timer expiry, interrupt, EOI or RTOS callback is manufactured by the board.

At 48 MHz, [the upstream timer's integer period calculation](https://github.com/qemu/qemu/blob/4fc49f46dc95d4a27de2509e7fceb2931e91faeb/target/arm/cpu.c#L1430-L1452) yields 20 ns per count, so a guest TVAL of 48,000 expires after approximately 0.96 ms of QEMU virtual time. This is a functional model limitation, not measured EXPEED performance or proof of real board timing. Reset security/banked CP15 behavior stays upstream; PPI 30 is not redirected to 29.

The MEMC layer added only `[0x04008ed0,0x04008f00)` as zero-initialized temporary RAM, exactly 48 bytes consumed by the original early stack path in the source-match analysis. The subsequent SMP layer adds the guest-produced release word `[0x04008ffc,0x04009000)` and the statically bounded 72-byte CPU1 SVC prefix `[0xb2b83fb8,0xb2b84000)`; its [run report](../../startup/smp.md) distinguishes mapped ranges from actual accesses. It is an explicit cold diagnostic RAM initialization, not proof of hardware reset contents. Addresses immediately below and above fail. Existing later RAM and bounded stack hypotheses are unchanged. Clock block `0x04281000`, IPC, BootROM and additional peripherals remain uncovered. The actual original run now stops at the first clock-block read, `0x0428102c`; no clock register response has been supplied.

## Synthetic verification and handoff

`scripts/devices.py` uses upstream `qemu.machine.QEMUMachine` to execute fifteen small synthetic ARM images (the original thirteen device contracts and two release-word boundary rejections), never recovered firmware. It checks MODE/TIM readback and WEOFF read/modify/write, reset read rejection, unsupported width/offset/profile rejection, NOR preinitialization/protection/backend failures, and the exact stack boundary. A separate fixture enables secure PPI 29, waits for the upstream timer, acknowledges IAR=29, verifies its active bit, disables the timer and EOIs it, then checks cleared active state, CNTFRQ and CBAR. CPU IRQ stays masked so the fixture can inspect controller state without inventing exception-vector firmware. Every fixture compares ROM readback with its input bytes.

CI retains the earlier four-byte self-loop registration/reset smoke and runs the new contracts after the official configure/Ninja build. Socket names live in short `/tmp/ng-*` directories. Local preparation checked Python syntax and disassembled fixture words with an existing Capstone installation. The parent subsequently completed the native build, all thirteen device fixtures and unchanged-original execution; their [evidence summary](../../startup/memc.md) identifies the new first stop. A passing synthetic test validates these modeled contracts only; it does not establish whole-camera boot, O0x178 arrival, RTOS/SMP service health, flash writing or real-camera acceptance.
